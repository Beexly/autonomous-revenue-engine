Pixel vs CAPI event_id Parity Checklist

Stop Shopify orders from counting twice in Meta. One shared event_id per purchase — verified in Events Manager, then proved against seven days of Shopify counts.

Meta only merges a Pixel (browser) event and a CAPI (server) event when event_name and event_id match. Same purchase, two ids = two conversions = a CPA that is a lie.

1 · How dedup actually works

Match key is the pair event_name + event_id — not email, not order number, unless you put that order number in the id. Pixel wants eventID (camelCase). CAPI wants event_id (snake_case). Different keys, identical string value. Purchase ≠ purchase. Do not hash the id — it is not PII. The 48-hour window is the outer limit; a nightly CAPI batch of events the Pixel already sent is a double-count.

Classic Shopify failure. Native Pixel (or the Facebook & Instagram channel) plus a separate CAPI app / custom Function / extra GTM. Each side mints its own id. Overview shows Browser and Server; dedup is 0%. Every paid order becomes two conversions. Budget scales into fiction. A thank-you Pixel using checkout token while CAPI uses order id will never match — pick one scheme, use it on both.

2 · Where to read the two ids

Pixel (browser)Events Manager → Test events → Browser row → eventID. Copy it.
CAPI (server)Same view → Server row → event_id. Paste next to the Pixel value. Character-for-character, or they do not merge.

Two un-merged rows for one test purchase: stop scaling. Disable the extra CAPI until ids match. Broken CAPI is worse than Pixel-only.

Last full 7 calendar days (not today). Same timezone both sides. This is the proof, not the Test events tab.

Shopify — how to pullAnalytics → Reports → Sales over time, same 7 dates, same timezone. Count paid orders (no draft, cancelled, test). Keep tax/shipping treatment identical to Meta, or accept that dollars drift more than counts.
